## 1. Core principle

**Actions and queries are type-agnostic. Only components branch by type.**

The `Item` table is one wide table with a `typeId` discriminator ([docs/item-types.md §4](docs/item-types.md)). The CRUD layer should mirror that shape: a single set of mutations that accepts whichever content fields apply, a single query module, and a single route — with the 7 types differing **only** in what the UI renders and validates.

The branching axis is **`ContentCategory`, not type**. There are 7 types but only 3 content shapes:

| Category | Types | Fields the form/preview handles |
|---|---|---|
| `TEXT` | Snippet, Prompt, Command, Note | `content` (+ `language` for Snippet) |
| `URL` | Link | `url` |
| `FILE` | File, Image | `fileUrl`, `fileName`, `fileSize` |

So every "branch by type" in this document is a **3-way switch on category**, plus two narrow per-type exceptions (Snippet shows a language picker; Image renders a thumbnail where File renders a filename row). Adding a custom type later — the planned Pro feature — requires zero new branches as long as it reuses an existing category.

## 2. File structure

New files are marked **new**; existing files that need extension are marked *extend*.

```
src/
├── actions/
│   └── items.ts                        ← NEW  all mutations, "use server"
│
├── lib/
│   ├── db/
│   │   └── items.ts                    ← extend  all queries (already exists)
│   ├── item-types.ts                   ← NEW  category registry (the missing "constants")
│   ├── validation/
│   │   └── item.ts                     ← NEW  Zod schemas (Zod not yet installed — see §9)
│   └── icons.ts                        ← unchanged  ICON_MAP
│
├── app/
│   └── items/
│       ├── layout.tsx                  ← NEW  auth + shell (see §4 for the route-group option)
│       ├── page.tsx                    ← NEW  all items
│       └── [type]/
│           └── page.tsx                ← NEW  items filtered by type slug
│
└── components/
    └── items/
        ├── ItemGrid.tsx                ← NEW  server  layout + empty state
        ├── ItemCard.tsx                ← move+extend from components/dashboard/
        ├── ItemPreview.tsx             ← NEW  server  category-branching read view
        ├── ItemDrawer.tsx              ← NEW  client  Sheet wrapper, read/edit
        ├── ItemForm.tsx                ← NEW  client  shared envelope fields
        ├── fields/
        │   ├── TextFields.tsx          ← NEW  client  content + language
        │   ├── UrlFields.tsx           ← NEW  client  url
        │   └── FileFields.tsx          ← NEW  client  upload → fileUrl/fileName/fileSize
        ├── ItemActions.tsx             ← NEW  client  favorite / pin / delete
        └── NewItemButton.tsx           ← NEW  client  opens drawer in create mode
```

**Why mutations go in `src/actions/` and queries stay in `src/lib/db/`** — this is exactly what [context/coding-standards.md](context/coding-standards.md) prescribes ("Server components fetch directly with Prisma; client components use Server Actions"), and it matches the existing split where [src/app/dashboard/page.tsx](src/app/dashboard/page.tsx) calls `getRecentItems()` directly with no API round-trip. `src/actions/` does not exist yet — `items.ts` would be the first file in it.

**Note a deviation from existing code:** every mutation written so far is a `POST` API route called with `fetch` from a client component (e.g. [ChangePasswordCard.tsx:42](src/components/profile/ChangePasswordCard.tsx#L42)). That was correct for auth — those endpoints need rate-limit headers, specific status codes, and NextAuth ownership. Item CRUD has none of those constraints, so Server Actions are the right call per the standards. The one exception is file upload, which needs a presigned-URL endpoint (`/api/upload`) and stays an API route.

## 3. The type registry — where type-specific logic lives

This is the file the research prompt expected at `src/lib/constants.tsx`. Proposed location: **`src/lib/item-types.ts`** (plain `.ts` — no JSX; icon components already live in [src/lib/icons.ts](src/lib/icons.ts)).

It holds **presentation and validation metadata keyed by category** — never by type name, and never anything already stored in the DB (name, slug, icon string, color, order all come from the `ItemType` row).

```ts
// src/lib/item-types.ts  — illustrative shape, not final code
import type { ContentCategory } from "@/generated/prisma/enums"

export interface CategoryConfig {
  /** Which Item columns this category populates. */
  contentFields: readonly ("content" | "url" | "fileUrl")[]
  /** Label for the primary content input in ItemForm. */
  contentLabel: string
  placeholder: string
  /** Show the language picker (Snippet only, gated further by slug). */
  supportsLanguage: boolean
  /** Requires a Pro subscription. */
  requiresPro: boolean
}

export const CATEGORY_CONFIG: Record<ContentCategory, CategoryConfig> = {
  TEXT: { contentFields: ["content"], contentLabel: "Content",  placeholder: "Paste your snippet, prompt, command or note…", supportsLanguage: true,  requiresPro: false },
  URL:  { contentFields: ["url"],     contentLabel: "URL",      placeholder: "https://…",                                   supportsLanguage: false, requiresPro: false },
  FILE: { contentFields: ["fileUrl"], contentLabel: "File",     placeholder: "",                                            supportsLanguage: false, requiresPro: true  },
}

export const LANGUAGES = ["typescript", "javascript", "python", "go", "rust", "sql", "bash", "dockerfile", "json", "yaml", "markdown"] as const
```

**`requiresPro: true` on FILE replaces the inline `category === "FILE"` check** currently hardcoded at [Sidebar.tsx:368](src/components/layout/Sidebar.tsx#L368) — one definition, consumed by the sidebar badge, the form, and the create action.

**Rules for what may live here:**

| ✅ Belongs in the registry | ❌ Does not |
|---|---|
| Which columns a category writes | Type name, slug, icon, color (DB) |
| Input labels and placeholders | Anything a user can customize |
| Language options for the picker | Business rules (free-tier limits → the action) |
| The Pro flag per category | Per-type `if (slug === "prompts")` chains |

If a genuine per-type (not per-category) behavior appears — e.g. the planned prompt optimizer only applying to Prompts — key it off `type.slug` **inside the component that needs it**, not in a shared branch table. Today there are exactly two such cases: Snippet's language picker, and Image's thumbnail vs File's filename row.

## 4. Routing: how `/items/[type]` works

### Route table

| Path | File | Renders |
|---|---|---|
| `/items` | `app/items/page.tsx` | every item the user owns, all types |
| `/items/snippets` | `app/items/[type]/page.tsx` | items where `type.slug === "snippets"` |
| `/items/prompts` | ↑ same file | … and so on for all 7 slugs |

`[type]` is a **single dynamic segment carrying the `ItemType.slug`** — matching the paths already hardcoded in the sidebar (`href={`/items/${type.slug}`}` at [Sidebar.tsx:372](src/components/layout/Sidebar.tsx#L372)) and the routing table in the project overview.

### Resolution flow

```
/items/snippets
  → app/items/layout.tsx     auth() → redirect("/sign-in") if no session
                             fetch sidebar data → <DashboardShell>
  → app/items/[type]/page.tsx
      params.type = "snippets"
      ① getItemTypeBySlug("snippets")  → ItemType row or null
      ② null → notFound()              → 404, never a Prisma error
      ③ FILE category + user not Pro   → upgrade prompt instead of the grid
      ④ getItemsByType(userId, type.id)
      ⑤ <ItemGrid items={…} type={…} />
```

Three things worth being deliberate about:

1. **Never trust the slug.** Resolve it to a real `ItemType` row and use `type.id` in the query. Filtering on a raw string would let `/items/anything` reach the database.
2. **Use `notFound()`, not a redirect,** for unknown slugs — a wrong URL is a 404, not an auth problem.
3. **No `generateStaticParams`.** These pages are per-user and session-gated; they must stay dynamic. `getSystemItemTypes` already runs per request in the layout.

### `/items` and `/items/[type]` are separate files

A catch-all `[[...type]]` would collapse them, but two files keeps each page's data call explicit and lets `/items` skip the type resolution entirely. The shared parts (grid, empty state) are components, so there is no duplication worth eliminating.

### Two blockers in the current routing setup

**(a) `/items` is not protected.** [auth.config.ts:36](src/auth.config.ts#L36) protects only `/dashboard` and `/profile`:

```ts
const isProtected = path.startsWith("/dashboard") || path.startsWith("/profile")
```

`/items` (and `/collections`) must be added, or the middleware lets unauthenticated users through to the layout — where the `auth()` check does catch them, but only after a wasted render. Fix the middleware **and** keep the layout check; defense in depth.

**(b) The shell layout is already duplicated.** [dashboard/layout.tsx](src/app/dashboard/layout.tsx) and [profile/layout.tsx](src/app/profile/layout.tsx) are byte-for-byte identical — same auth check, same `Promise.all`, same `DashboardShell`. Adding `items/layout.tsx` makes three copies.

The clean fix is a route group:

```
src/app/(app)/layout.tsx        ← the one shell layout
src/app/(app)/dashboard/page.tsx
src/app/(app)/profile/…
src/app/(app)/items/…
src/app/(app)/collections/…
```

Route groups don't affect URLs, so `/dashboard` and `/profile` keep working. But this moves existing files, and [context/ai-interaction.md](context/ai-interaction.md) says to ask before refactors — **this is a decision to make explicitly**, not to fold silently into the CRUD feature. If deferred, `items/layout.tsx` becomes copy #3 and the debt grows.

## 5. Data fetching (`src/lib/db/items.ts`)

Extends the existing module. Every function takes `userId` as its first parameter — the convention established when the dashboard was scoped to the session ([src/lib/db/items.ts](src/lib/db/items.ts)).

### `ItemWithMeta` must be widened first

The current interface ([items.ts:13-25](src/lib/db/items.ts#L13-L25)) selects `content` and `language` but **omits `description`, `url`, `fileUrl`, `fileName`, `fileSize`** — so URL and FILE payloads never reach the UI at all. Nothing can render a Link or a File until this is fixed. Add all five, and add `id`-bearing `collections` if the drawer is to show membership.

### New functions

| Function | Purpose | Notes |
|---|---|---|
| `getItemTypeBySlug(slug)` | resolve route param → `ItemType` | wrap in React `cache()` — layout and page both need it |
| `getItemsByType(userId, typeId, opts?)` | grid for `/items/[type]` | `opts`: `sort`, `favoritesOnly`, `take`/`skip` |
| `getAllItems(userId, opts?)` | grid for `/items` | same options object |
| `getItemById(userId, id)` | drawer / edit view | **must include `userId` in the `where`** — see §8 |

Reuse the existing `serializeItem()` helper so `Date` fields cross the server/client boundary as ISO strings, as they already do.

### Query notes

- **Ordering** should follow the established dashboard pattern: `[{ isPinned: "desc" }, { lastUsedAt: { sort: "desc", nulls: "last" } }, { updatedAt: "desc" }]` — pinned first, then recency. The `[userId, isPinned]` and `[userId, lastUsedAt]` indexes already exist in the schema.
- **The tag include is an N+1 risk at scale.** `tags: { include: { tag: … } }` is one extra join per query, which Prisma batches fine for a page of items — but if the grid grows to hundreds of rows without pagination it will hurt. Add `take`/`skip` from the start.
- **Counting for the free-tier gate** belongs in the action, not here.

## 6. Mutations (`src/actions/items.ts`)

One file, `"use server"` at the top, one exported function per operation. All follow the `{ success, data, error }` shape mandated by the coding standards.

| Action | Signature | Responsibilities |
|---|---|---|
| `createItem` | `(input: CreateItemInput)` | auth → validate → free-tier check → Pro check → tag upsert → create → revalidate |
| `updateItem` | `(id, input: UpdateItemInput)` | auth → validate → **ownership-scoped update** → revalidate |
| `deleteItem` | `(id)` | auth → **ownership-scoped delete** → revalidate |
| `toggleFavorite` | `(id)` | auth → scoped toggle → revalidate |
| `togglePin` | `(id)` | auth → scoped toggle → revalidate |
| `touchItem` | `(id)` | sets `lastUsedAt = now()`; fire-and-forget on copy/open |

### The uniform shape of every action

```ts
export async function createItem(input: CreateItemInput) {
  try {
    const session = await auth()
    if (!session?.user?.id) return { success: false, error: "Not authenticated" }

    const parsed = createItemSchema.safeParse(input)
    if (!parsed.success) return { success: false, error: parsed.error.issues[0].message }

    // …business rules, then the Prisma call…

    revalidatePath("/items")
    revalidatePath(`/items/${type.slug}`)
    revalidatePath("/dashboard")
    return { success: true, data: item }
  } catch (err) {
    console.error("createItem failed", err)
    return { success: false, error: "Could not create item." }
  }
}
```

Three details that are easy to get wrong:

**Validation is a discriminated union on category, resolved server-side.** The client sends `typeId`; the action loads the `ItemType`, reads its `category`, and picks the matching branch. Never let the client assert its own category — that would let a free user post a `TEXT` payload against the File type, or vice versa.

```
TEXT → content required, non-empty; url/fileUrl must be absent
URL  → url required, must parse as http(s); content/fileUrl absent
FILE → fileUrl + fileName + fileSize required; content/url absent
```

**Tags need `connectOrCreate`.** `Tag.name` is globally unique across all users ([schema.prisma:145](prisma/schema.prisma#L145)), so two users tagging `react` share one `Tag` row and are kept apart only by the `ItemTag` join. Creating a tag blindly will violate the unique constraint.

**`revalidatePath` must cover every surface showing the item** — the type page, `/items`, `/dashboard` (stats, pinned, recent), and any collection page it belongs to. Missing one leaves stale counts in the sidebar, which reads `getSystemItemTypes()` in the layout.

### Business rules that live here (not in components)

- **Free-tier limit** — `FREE_ITEM_LIMIT = 50`, checked with `prisma.item.count({ where: { userId } })` before create, per the project overview. Collections get `FREE_COLLECTION_LIMIT = 3` when that feature lands.
- **Pro gate for FILE** — `CATEGORY_CONFIG[category].requiresPro`. A client-side check is a UX affordance; this one is the actual enforcement.

Both depend on an `isProUser()` helper that **does not exist yet** — [src/lib/features.ts](src/lib/features.ts) exports only `isEmailVerificationEnabled()`. The project overview specifies the env-driven pattern (`true` in development, `user.isPro` otherwise); it needs writing before the gate can be enforced.

## 7. Component responsibilities

Server by default, `"use client"` only where there is state or an event handler — the split the codebase already follows.

### Server components

**`ItemGrid`** — pure layout. Takes `items` and optional `type`, renders the responsive grid (`grid-cols-1 sm:grid-cols-2 lg:grid-cols-3`, matching the dashboard), and owns the **empty state**, which should be type-aware: "No snippets yet" with a create button reads far better than a generic blank. No data fetching, no state.

**`ItemCard`** — one card. Currently at [components/dashboard/ItemCard.tsx](src/components/dashboard/ItemCard.tsx) and already correctly data-driven for icon and color (`ICON_MAP[type.icon]`, `${color}20` backgrounds). Two changes needed: move it to `components/items/`, and delegate its content preview to `ItemPreview` so Link and File items stop rendering blank ([docs/item-types.md §6](docs/item-types.md)).

**`ItemPreview`** — **the primary type-branching component**, and the single place the 3-way switch on category lives:

```
TEXT → <pre> excerpt, monospace, line-clamp-3   (today's behavior)
URL  → hostname + favicon + truncated href
FILE → Image: <Image> thumbnail from fileUrl
       File:  filename + humanized fileSize
```

Everything else — badge, title, tags, timestamp — stays type-agnostic in the card.

### Client components

**`ItemDrawer`** — read/edit surface. Wraps the existing `Sheet` primitive ([src/components/ui/sheet.tsx](src/components/ui/sheet.tsx), Base UI Dialog) with `side="right"`; the sidebar already uses `Sheet` for its mobile drawer, so no new dependency. Owns open/closed state and read-vs-edit mode. Calls `touchItem` on open so `lastUsedAt` and the "Recent" list actually work.

**`ItemForm`** — the create/edit form. Owns the **shared envelope only**: title, description, type selector, tags, collection assignment. It renders exactly one field component based on the selected type's category, and calls `createItem`/`updateItem`. Errors surface inline; success fires a Sonner toast — the pattern from [ChangePasswordCard.tsx:51-56](src/components/profile/ChangePasswordCard.tsx#L51-L56).

**`fields/TextFields` · `fields/UrlFields` · `fields/FileFields`** — one per category, each owning only its own inputs. `TextFields` shows the language picker when `supportsLanguage` and the slug is `snippets`. `FileFields` is the only one with real complexity: presigned-URL request → direct R2 upload → progress → hand `fileUrl`/`fileName`/`fileSize` back to the form. **R2 is not wired yet**, so this component should be built last and stubbed until then.

**`ItemActions`** — favorite/pin/delete buttons. Optimistic UI via `useOptimistic` or `useTransition`; delete asks for confirmation using the inline expand/confirm pattern from [DeleteAccountCard](src/components/profile/DeleteAccountCard.tsx) rather than a new Dialog primitive.

**`NewItemButton`** — opens the drawer in create mode, pre-selecting the current route's type. This is what the currently inert "New item" button at [TopBar.tsx:42](src/components/layout/TopBar.tsx#L42) should wire up to.

### Responsibility boundaries at a glance

| Concern | Owner |
|---|---|
| Which fields exist for a category | `CATEGORY_CONFIG` (registry) |
| How a category *renders* | `ItemPreview`, `fields/*` |
| How a category *validates* | `lib/validation/item.ts`, enforced in the action |
| Whether the user *may* create it | `actions/items.ts` |
| Icon and color for a type | the `ItemType` DB row + `ICON_MAP` |

## 8. Security requirements

Non-negotiable, and cheap to get right if designed in from the start.

**Every mutation must scope by `userId`, not just by `id`.** `deleteItem(id)` that runs `prisma.item.delete({ where: { id } })` after only checking *that* a session exists lets any signed-in user delete any other user's item by guessing a cuid. Use the scoped-batch form so ownership is part of the query:

```ts
const result = await prisma.item.deleteMany({ where: { id, userId: session.user.id } })
if (result.count === 0) return { success: false, error: "Item not found." }
```

The same applies to `updateItem`, both toggles, `touchItem`, and `getItemById`. Returning "not found" rather than "forbidden" also avoids confirming that someone else's item exists.

**Never trust client-supplied category, `isPro`, or `userId`.** All three come from the server: category from the `ItemType` row, Pro status from the session user, `userId` from `auth()`.

**Validate `url` before storing.** A Link item's `url` will be rendered as an `href`; without a scheme check, `javascript:` URLs become stored XSS. Allow `http:` and `https:` only.

**Sanitize on render, not on store.** If Markdown rendering is added for Notes and Prompts, escape at render time; storing raw content is correct.

## 9. Prerequisites and open decisions

Things that must be resolved before or during implementation:

1. **Zod is not installed.** [context/coding-standards.md](context/coding-standards.md) mandates "Validate all inputs with Zod", but it is absent from [package.json](package.json), and every auth route hand-rolls its checks with `if` statements ([register/route.ts:26-36](src/app/api/auth/register/route.ts#L26-L36)). Item CRUD has a genuine discriminated union to validate, which is where Zod earns its keep — **install it, or accept hand-rolled validation and update the standards.**

2. **`isProUser()` does not exist.** Needed by `createItem` for the FILE gate and by the free-tier limit. The project overview gives the intended env-driven implementation.

3. **The shell layout duplication / route-group refactor** (§4b) — a decision to make before adding a third copy.

4. **Middleware protection for `/items`** (§4a) — a two-word change, but easy to forget.

5. **`ItemWithMeta` must be widened** (§5) — nothing type-related renders correctly until it is.

6. **R2 is not wired.** No `R2_*` env vars are live and no `/api/upload` route exists, so File and Image are unbuildable end-to-end. Build the 5 non-FILE types first; `FileFields` and the upload route are a separate, later slice.

7. **`src/lib/mock-data.ts` is dead code** carrying a stale item-type ordering. It should be deleted during this work so it stops being mistaken for a reference — but per [context/ai-interaction.md](context/ai-interaction.md) ("Never delete files without clarification"), that needs a green light.

## 10. Suggested build order

Each step leaves the app in a working, buildable state.

| # | Slice | Delivers |
|---|---|---|
| 1 | Widen `ItemWithMeta`; add `getItemTypeBySlug`, `getItemsByType`, `getAllItems`, `getItemById`; add `/items` to the middleware matcher | queries ready, nothing user-visible |
| 2 | `src/lib/item-types.ts` registry; `ItemPreview`; move + extend `ItemCard` | Links and Files stop rendering blank on the dashboard |
| 3 | `app/items/layout.tsx`, `page.tsx`, `[type]/page.tsx`, `ItemGrid` | **read-only browsing works** — the sidebar's 7 links stop 404ing |
| 4 | Zod + `lib/validation/item.ts`; `actions/items.ts` with `createItem`/`updateItem`/`deleteItem` | mutations exist, callable |
| 5 | `ItemForm` + `TextFields` + `UrlFields`; `ItemDrawer`; wire `NewItemButton` | **full CRUD for the 5 free types** |
| 6 | `ItemActions`, `togglePin`, `toggleFavorite`, `touchItem` | pin/favorite/recency working end-to-end |
| 7 | `isProUser()`; free-tier limit in `createItem`; Pro gate on FILE | limits enforced |
| 8 | `/api/upload` + R2 + `FileFields` | File and Image types usable |

Steps 1-3 are read-only and carry no mutation risk. Step 5 is the first point at which the app can write items, and is where the §8 ownership scoping must be verified.
